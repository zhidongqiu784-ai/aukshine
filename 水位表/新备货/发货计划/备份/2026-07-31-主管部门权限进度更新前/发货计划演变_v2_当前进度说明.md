# 发货计划演变 v2 当前进度与新会话交接

更新时间：2026-07-29

当前代码基线：`178d3bf 修复发货计划最低量富余结转`

用途：新开 Codex 会话时，优先完整读取本文，再读取本文列出的正式文件。本文只记录已经实现、已经核对或明确待验证的事实；动态生产数据均标注核对日期，不把推测写成完成状态。

## 1. 项目目标

把原来由销售手填的模拟发货计划，逐步替换为系统自动计算的 `shipment_plan_v2` 发货建议，并把真实在途与新算法建议共同推演到 `daily_sales.v2_*`，最后由 NocoBase JS Block 页面展示并支持人工调整、审核和应用。

核心原则：

- 计划按 `country + asin + shop = 合计` 生成，不在本模块分配未来具体销售店铺。
- 页面主数字只代表算法建议发货量，不把真实在途加进主数字。
- 真实在途仍参与未来库存和安全库存天数推演。
- 人工拖动只修改算法建议，不修改真实在途。
- 旧销售手填模拟计划与 `shipment_plan_v2` 保持隔离。
- V2 推演与普通库存一致：缺货期间未成交需求不结转，卖完即停止扣减欠货需求。

## 3. 当前数据表职责

### 3.1 `daily_sales`

提供销量、普通水位基础和 V2 推演结果。

关键字段：

- `maybe_sales`：预计销量，需求计算优先使用。
- `weighted_sales`：加权基准销量，`maybe_sales` 为空时回退使用。
- `inventory`、`days_for_sale`、`add`、`on_the_way`：普通水位口径。
- `v2_add`：V2 当天入库量，包含有效真实补货与新算法模拟计划。
- `v2_inventory`：V2 推演库存。
- `v2_days_for_sale`：V2 推演安全库存天数。
- `v2_on_the_way`：V2 推演在途。
- `v2_calculated_at`：V2 本次推演时间，用于避免较早任务覆盖较晚结果。

页面过去和未来销量表均已有“含 V2 列”版本：

```text
水位表/水位表详情/水位表_销量表格JS版含v2列.js
```

旧版已保留为：

```text
水位表/水位表详情/水位表_销量表格JS版不含v2列.js
```

### 3.2 `simulate_shipment`

保存系统生成的模拟发货建议。

V2 隔离条件：

```text
plan_source = shipment_plan_v2
shop = 合计
```

主要字段：

- `number`：建议发货数量，也是页面格子和图表节点的主数字。
- `date`：建议发货日期。
- `add_date`：预计入库日期。
- `channel`：物流渠道。
- `warehouse_days`：入仓天数。
- `season`：淡季或旺季。
- `v2_calculation_snapshot`：生成或重算时保存的公式输入、目标库存和建议量计算数据。

页面已经移除“（生成快照）”字样，但仍读取 `v2_calculation_snapshot` 展示计算过程。该字段是数据库中的计划计算依据，不是页面临时数据。

### 3.3 真实在途来源

普通水位和页面当前使用 `expected_inventory`：

```text
qty_shipped > 0
remaining > 0
```

- `remaining`：仍未入库的真实在途数量。
- `expected_storage_time`：预计入库日期。
- `qty_shipped = 0`：旧销售手填模拟计划，不进入 V2 真实在途。

但是截至 2026-07-28，三个正式 V2 推演 SQL 的真实在途实现并未直接读取 `expected_inventory`，而是内联使用：

```text
delivery_note.quantity_shipped - fba_ship.received
```

涉及：

- `../../工作流/更新水位表/10-发货计划演变-v2水位推演.sql`
- `../../工作流/【在用·自动】每周生成模拟计划 v3.8(单周口径+执行约束层+活动前置)/02-发货计划演变 v2 水位推演.sql`
- `../../工作流/【在用·测试】发货计划演变-v2-应用计划（统一安全闸）/02-重算对应ASIN水位.sql`

这会造成普通在途、页面真实在途和 V2 在途可能来自不同计算链路。团队经验口径要求 V2 真实在途以 `expected_inventory` 为准；当前尚未统一，属于待处理风险，不能写成已经解决。

### 3.4 `shipment_plan_change_v2` 与日志表

- `shipment_plan_change_v2`：保存修改申请、审核状态、乐观锁信息和应用结果。
- `shipment_plan_change_log_v2`：保存提交、审核和应用过程日志。

### 4.2 预计入库日

```text
预计入库日 = 发货日 + 物流天数 + 入仓天数
```

- 物流天数读取物流渠道时效配置。
- 入仓天数读取 `v3_cfg_cycle_param`。
- 淡季使用 `warehouse_off`。


## 5. 当前建议量算法状态

这里必须区分“建议量原始缺口计算层”和“执行约束层”。截至 2026-07-29，自动生成与手动重算只有执行约束层保持一致，原始缺口算法仍不相同，不能写成两条工作流已经完全统一。

### 5.1 已统一的执行约束层

正式文件：

```text
水位表/工作流/【在用·自动】每周生成模拟计划 v3.8(单周口径+执行约束层+活动前置)/01-生成模拟计划.sql
水位表/工作流/【手动执行认这条】重算现有模拟计划 v3.7(单周口径+执行约束层)/01-重算现有W1-W7建议数量.sql
```

两条工作流共同执行：

```text
原始缺口
→ 先扣除前周因最低发货量或整箱多发形成的富余
→ 按箱入数向上取整
→ 仍需发货且低于最低发货量时补到有效最低量
→ 本周多发富余继续抵扣后周
```

快照中保留以下排查字段：

```text
prior_constraint_surplus
adjusted_gap_after_prior_surplus
qty_boxed_after_prior_surplus
constraint_surplus_after
```

因此如果 W1 已经因为最低发货量或箱入数多发，W2/W3 会先消耗这部分富余，再判断是否需要继续发货，避免每一周都独立补到 60。

### 5.2 每周自动生成的原始缺口

自动工作流节点 01 除了计算数量，还负责生成渠道、发货日期、到货日期和活动前置。普通周以 7 天服务期为主；活动重叠时服务期可能扩展到 14 天，并包含下单周特殊分支。

```text
服务期需求
− 服务期开始日 daily_sales.v2_inventory
→ 得到自动生成原始缺口
```

自动生成不会像手动重算那样，从服务期开始日逐日倒推到该计划的实际 `add_date` 重新构造到货日库存。

### 5.3 手动重算的原始缺口

手动工作流只重算已经存在的 W1-W7，不重新选择渠道或生成班期。服务期固定为 7 天，并结合当前库存、真实补货和已确定计划重建基线，再从服务期开始日倒推到实际到货日。

```text
固定 7 天服务期需求
+ 到货日至服务期前的过渡需求
− 不发本批时到货日预计库存
→ 得到手动重算原始缺口
```

手动重算不包含活动前置、服务期扩展、渠道选择和下单周生成分支。

### 5.4 执行约束层样例

2026-07-28 排查 `FR / B0GX9TWLD7 / 合计` 时发现，页面曾出现多个周次小缺口分别被补到 60 的结果。原因是执行约束层按周独立处理，且手动重算 SQL 的默认等级匹配条件未覆盖 `level_scope = '默认...'` 的配置。

修复后本地算法以顺序递推为准，示例原始缺口 `[42, 6, 15, 15, 21, 120, 30]`、最低发货量 60、箱入数 12 时，结果为：

| 周次 | 原始缺口 | 前序富余抵扣后缺口 | 最终建议量 | 结转富余 |
|---|---:|---:|---:|---:|
| W1 | 42 | 42 | 60 | 18 |
| W2 | 6 | 0 | 0 | 12 |
| W3 | 15 | 3 | 60 | 57 |
| W4 | 15 | 0 | 0 | 42 |
| W5 | 21 | 0 | 0 | 21 |
| W6 | 120 | 99 | 108 | 9 |
| W7 | 30 | 21 | 60 | 39 |

注意：以上是算法样例推导，不等同于线上当前数据库结果。要判断线上是否已经生效，必须以对应工作流执行后的 `simulate_shipment.v2_calculation_snapshot` 和页面刷新结果为准。

### 5.5 当前差异结论

2026-07-29 已只读核对线上和本地 SQL：两条工作流的最低发货量、箱入数和前周富余抵扣已经同步，但原始缺口层没有统一。活动周、下单周、到货间隔不规则或渠道日期变化时，两条工作流可能给出不同建议数量。

未锁定的计划后续被每周自动工作流刷新时，会重新使用自动生成算法，因此手动重算结果不是永久覆盖自动生成公式。

## 6. V2 库存和在途递推

### 6.1 今日锚点

节点 10 位于普通水位节点 09 之后。普通合计行今日 `inventory` 已包含旧 `add`，因此 V2 先执行：

```text
今日真实库存锚点 = inventory - old add
今日 V2 库存 = 今日真实库存锚点 + 今日 v2_add
```

### 6.2 未来库存

与普通库存缺货口径一致：

```text
如果前一天库存 - 前一天需求 < 0，且今天有正补货：
    今天 V2 库存 = 今天的正补货量
否则：
    今天 V2 库存 = 前一天库存 - 前一天需求 + 今天补货
```

因此库存为 0 后不会继续累计负库存，也不会把缺货期间未成交需求从下一批补货中扣回。

### 6.3 负补货和在途

- `v2_add > 0`：到货，库存增加，在途减少。
- `v2_add < 0`：补货修正，库存减少，在途恢复等量数量。
- `v2_on_the_way` 按“未来正补货总量减去截至当天累计净补货”递推。

### 6.4 安全库存天数

```text
v2_inventory <= 0      → v2_days_for_sale = 0
weighted_sales > 0     → FLOOR(v2_inventory / weighted_sales)
其他情况               → 0
```

### 6.5 三套 V2 水位算法差异

2026-07-29 已对比每周自动水位、手动重算水位和每小时水位节点：

| 算法点 | 每周自动水位 | 手动重算水位 | 每小时水位 |
|---|---|---|---|
| `v2_inventory` | 有 | 有 | 有 |
| `v2_days_cover` | 有 | 有 | 有 |
| `v2_sale_inventory` / `v2_sale_days_cover` | 有 | 有 | 有 |
| 风险等级和原因 | 有 | 无 | 有 |
| 超签收形成的负补货 | 忽略 | 保留 | 保留 |
| `v2_on_the_way` | 未来补货求和 | 正补货总量减累计净补货 | 正补货总量减累计净补货 |

三套 V2 水位 SQL 的真实补货都内联读取 `delivery_note.quantity_shipped - fba_ship.received`，当前均未直接读取 `expected_inventory`。

手动重算后，库存和两套可撑天数会立即刷新，但风险等级和原因要等待下一次每小时水位工作流运行。

### 10.2 每周自动链路

```text
周日 23:50  更新水位表
周一 00:08  每周生成模拟计划
             节点 01 生成建议
             节点 02 重算 V2
             节点 03 写入 V21 历史基线快照
```

当前周任务使用周日 23:50 的水位结果，不会等待周一 00:50。时间差 18 分钟，但不是严格的“周一当天先更新水位再生成计划”。是否调整时间尚未决定。

### 10.3 手工运行：生成新计划

```text
1. 执行“更新水位表”
2. 等待成功
3. 执行“每周生成模拟计划”

```

“更新水位表”只刷新普通水位和 V2 水位，不会重新计算已有建议量。

### 10.4 手工运行：按最新算法重算已有计划

```text
1. 执行“更新水位表”
2. 等待成功
```

“每周生成模拟计划”和“重算现有模拟计划”不是固定串行的两个步骤：

- 需要生成新一周计划时运行前者。
- 只需把已有计划切换到最新重算公式时运行后者。
- 未明确目的时不要连续运行两个工作流，否则后运行者会再次更新已有建议。
